### Как запустить сайт и посмотреть в браузере (пошагово)
1. Открыть VS Code с папкой `C:\apetit-site`.
2. Открыть терминал: меню **Terminal → New Terminal** (или `Ctrl` + `` ` ``).
3. Ввести `npm run dev` и нажать Enter. Через несколько секунд появится
   строка вида `- Local: http://localhost:3000`.
4. Открыть в браузере адрес **http://localhost:3000** — это и есть сайт.
   Внизу слева будет маленький кружок с буквой N — это служебный значок
   режима разработки, на настоящем сайте его не будет.
5. Остановить сайт: щёлкнуть в терминал и нажать `Ctrl` + `C`.

- `npm run build` — собрать сайт как для боевого сервера (проверка, что всё
  компилируется);
- `npm run lint` — проверка кода линтером;
- `npm test` — быстрые тесты; `npm run test:e2e` — тест в настоящем браузере
  (сам поднимает сайт и сам его гасит).

### CSP: почему без nonce

Проверил по документации Next 16 (в node_modules и через context7): nonce
работает **только если каждая страница собирается на сервере при каждом
заходе**. Тогда меню перестало бы быть готовым заранее (SPEC §9.5), каждый
заход считался бы на Cloudflare — медленнее и дороже. Поэтому рабочий вариант:
`script-src 'self' 'unsafe-inline'`. Встроенные скрипты разрешены (без них
Next не оживит статическую страницу), но **скрипты с любых других сайтов
запрещены**, данные уходят только на наш сервер, страницу нельзя встроить в
чужой сайт. `style-src 'unsafe-inline'` — анимации и размеры вывесок задаются
через атрибут style. `'unsafe-eval'` — только в режиме разработки (так требует
React). Экспериментальный SRI Next не решает проблему встроенных скриптов —
не включал.

По дороге нашёл: библиотека zod «на пробу» вызывает eval и получает запрет
CSP (в консоли — нарушение на меню и оформлении). Включил её официальный
режим без eval (`jitless`, файл `src/lib/zod.ts`; весь код теперь берёт zod
оттуда — это сторожит тест). Правила проверки заказа не изменились.

## 2026-09-21 — Этап 5 — движок анимаций (WebGL) и живой фон

### 1. Движок — `src/motion`

Архитектура в десяти строках:

1. `engine.ts` — одиночка на весь сайт: один `<canvas>` на весь экран (за
   контентом, клики проходят сквозь), один контекст WebGL2 (запас — WebGL1
   с `OES_standard_derivatives`; нет ни того, ни другого — движок молча
   выключен, сайт работает), один цикл кадров.
2. Эффект — это **слой**: `{ id, zIndex, init(gl), render(gl, frame), dispose(gl) }`.
   Слой сам владеет своими буферами, шейдерами и текстурами.
3. `engine.add(layer)` / `engine.remove(id)` — подключить и отключить.
4. Кадр даёт слоям `{ t, dt, width, height, dpr, scroll }`: `t` — секунды,
   `dt` — миллисекунды, `scroll` — общая сглаженная прокрутка.
5. `scroll.ts` — это сглаживание: `k = 1 − (1 − ease)^(dt/16.67)`,
   `smooth += (target − smooth) × k`. Слой сам умножает на свой `parallax`.
6. `quality.ts` — четыре уровня: 1) плотность до 1.5 · 2) плотность 1.0
   · 3) 30 кадров/с · 4) стоп. Первые две секунды движок считает кадры:
   меньше 50 — уровень ниже, ещё раз меньше 50 — ещё ниже, меньше 40 — стоп.
   Уровень живёт в sessionStorage и сам не повышается.
7. `pause.ts` — паузы по причинам. Цикл идёт, только когда причин нет.
   Встроены: спрятана вкладка, открыт лист блюда, открыта корзина, страница
   сама едет к категории. Причина — любая строка, будущая анимация бургера
   возьмёт свою.
8. «Уменьшить движение» — один кадр, цикл выключен, слои получают `t = 0`
   и `scroll = 0`. Потеря контекста — тихо уровень 4, без ошибок в консоли.
9. Движок подгружается **после показа страницы** (отдельный кусок кода,
   `ssr:false`), холст проявляется за 300 мс. На скорость первого экрана
   не влияет — цифры ниже.
10. Настройки всех эффектов — `src/config/motion.json` (читается при сборке),
    правятся в панели `/dev/motion`.

### 3. Схема (окончательная)

`src/config/alerts.json`:
```json
{ "reminderEvery": 2, "reminderMax": 15, "ownerAt": 12,
  "ownerRepeatEvery": 10, "ownerMax": 3 }
```

Отсчёт от времени заказа, две независимые дорожки:
- **точке** — `⏰ Comanda #1042 așteaptă — X minute` каждые 2 минуты, начиная
  с 2-й, максимум 15 раз (то есть 30 минут). X — сколько заказ уже ждёт;
  минуты склоняются правильно на обоих языках (`2 minute`, `20 de minute`,
  `21 минута`, `25 минут`);
- **владельцам** — `⚠️ Apetit Centru nu a preluat comanda #1042. Au trecut 12
  minute. Tel. punct: 067 578 757` на 12-й минуте, потом каждые 10 минут,
  всего 3 раза (12, 22, 32).

На 12-й и 22-й минуте дорожки совпадают — уходят оба сообщения. Тревог по три
сообщения 🚨 больше нет. Нажали «Am preluat» — всё прекращается мгновенно, на
любом шаге. Для Otaci — те же тексты по-русски.

**Потолки — главная защита**: когда обе дорожки пройдены (15 напоминаний и 3
сообщения владельцам), заказ выпадает из выборки самим запросом к базе и
больше не звонит никогда, даже если про него забыли.

## 2026-09-22 — Этап 5 — фон по ширине экрана, цвет фона на выбор, правки по контактам и ru-названиям

### 1. Фон — масштаб от ширины экрана

Раньше масштаб рисунка задавался в пикселях (`scale: 900` — 900 пикселей на
клетку узора). Экран компьютера 1900 px вмещал два оборота рисунка, телефон
390 px — меньше половины, поэтому на телефоне линии казались крупными,
редкими и толстыми.

Теперь в `src/config/motion.json` вместо `scale` стоит **`tilesAcross: 2.11`** —
сколько раз рисунок укладывается по ширине экрана. Масштаб считается каждый
кадр: `uScale = ширина холста в пикселях экрана / tilesAcross`. Значит поворот
телефона и любое изменение размера окна учитываются сами собой.

Почему 2.11: прежние 900 px на клетку при ширине экрана Амяна 1900 px дают
1900 / 900 = 2.111 оборота. Округлил до 2.11 (разница с точным значением —
полпроцента, глазом не видно, зато число ложится на шаг ползунка). Вид на
компьютере 1900 px остался ровно как был; на узком компьютере (1280 px) и на
телефоне рисунок стал плотнее — в этом и была задача.

Толщина линии (`width: 0.8`) не тронута и от масштаба не зависит: она берётся
из производной поля (`fwidth`), то есть всегда одна и та же в пикселях экрана.
На скриншотах телефона линии не стали тоньше, чем были, — менять значение не
понадобилось.

В панели `/dev/motion` ползунок «Масштаб рисунка» заменён на **«Плотность

## 22.09.2026 · Задача 10 — белые линии на iPhone, тёплый фон, ответы архитектора

### 1. Линии фона на iPhone были белые — починено

Причина именно та, что назвал архитектор: **premultiplied alpha**. Холст
просили создать с «цвет НЕ домножен на прозрачность», а Safari на iPhone
всё равно складывает холст со страницей так, будто цвет уже домножен. Из-за
этого полупрозрачная серая линия выходила светлее фона — то есть белой.

Сделано ровно три правки, они работают только все вместе:

| Где | Было | Стало |
|---|---|---|
| `src/motion/gl.ts` | `premultipliedAlpha: false` | `premultipliedAlpha: true` |
| шейдеры в `src/motion/layers/contours.ts` | `vec4(uC, line * uA)` | `float a = line * uA; vec4(uC * a, a)` |
| смешивание там же | `SRC_ALPHA / ONE_MINUS_SRC_ALPHA` | `ONE / ONE_MINUS_SRC_ALPHA` |

`alpha: true` оставлен, формула линий не тронута, настройки в
`motion.json` не менялись.

**Как проверил на компьютере.** Снял меню и посчитал пиксели картинки:
на участке без фото и текста **нет ни одного пикселя светлее фона** —
линии теперь только затемняют, как и должны. Самый тёмный оттенок линии —
примерно `#D3CCC4`, это Ash 45 % поверх кремового.

**На настоящем iPhone не проверял — проверить должен Амян.** У меня Windows,
Safari тут нет, а хром на телефоне ведёт себя иначе и баг не показывает.

   компьютера в домашней сети (см. п. 6). Если адрес сменился, узнать новый:
   в PowerShell команда `ipconfig`, строка «IPv4-адрес».

## 22.09.2026 · Задача 11 — Safari превращал IDNO в телефон и ронял гидратацию

### Что было

Safari на iPhone умеет сам находить в тексте «телефоны», «адреса» и «даты» и
дописывать вокруг них свои ссылки — уже в готовую страницу. IDNO в подвале
(`1023607001174`) — тринадцать цифр подряд, и Safari принимал их за номер.
React получал разметку, которую не писал, и падал с «Hydration failed» на
весь экран (в рабочем режиме это выглядело бы как молчаливая пересборка
страницы, но всё равно неправильно).

### Что сделано

**1. Запрет в метаданных — главное.** В `rootMetadata()`
(`src/lib/seo.ts`) добавлен `formatDetection`. Next сам превращает его в
тег, который и просил архитектор:

```html
<meta name="format-detection" content="telephone=no, date=no, address=no, email=no" />
```

`rootMetadata()` зовут оба корневых layout — румынский `src/app/(ro)` и
русский `src/app/ru`, — поэтому тег стоит на всех страницах обоих языков.
Страницы его не перебивают: они собирают метаданные через `pageMetadata()`,
где этого поля нет, а Next такие поля наследует от корня (есть тест).

Порядок слов в теге не мой — так его собирает сам Next (список ключей в
`next/dist/esm/lib/metadata/metadata.js`), и он совпадает с заданием.

**2. Вторая защита в подвале.** В `src/components/menu/site-footer.tsx`
появился маленький компонент `Idno`: цифры разложены по двум отдельным
элементам (`1023` и `607001174`), поэтому тринадцати цифр подряд в разметке
просто нет — принимать за номер нечего. На вид и при копировании строка та
же: «IDNO 1023607001174».

Честная оговорка: элемента, который Safari «не трогает», в вебе не
существует — официальный способ отключить эту самодеятельность один, и это
мета-тег из пункта 1. Разбивка цифр — не замена ему, а страховка на случай,
если тег когда-нибудь потеряется при правке метаданных.

**3. Настоящие ссылки tel: не пострадали** — ни на контактах, ни в
подтверждении заказа, ни в карточках точек. Запрет `telephone=no` запрещает
Safari *выдумывать* ссылки, а те, что мы ставим сами, он открывает как
обычно.

### 1. Тень под фото

**Главное про скорость.** `filter: blur()` не использован нигде: на меню 47
плиток, полсотни размытий на кадр телефон не вытянет. Каждый слой — эллипс

Проверка не на словах: отрисовал в браузере рядом эталон (`filter: blur`, как

было «+2·blur»; я сперва сделал даже вдвое шире для точности, но потом

корзине не тронуты**: у них осталась прежняя плоская лужица.

### 3. Подъём при прокрутке («aterizare»)

Новый слой движка `products` (`src/motion/layers/products.ts`). На холсте он
ничего не рисует — берёт тик и время кадра и пишет `transform` живым
элементам. Физика — ровно `loop()` из демо: своё сглаживание прокрутки,
скорость, цель подъёма `1 − exp(−|v|/12)` и пружина (вверх жёсткая 320, вниз
мягкая 130, затухание критическое — без дрожи).

Что сделано, чтобы это не съедало кадры:

- обновляются **только карточки в пределах экрана ±200px**; кто в экране,
  помнит `IntersectionObserver` — на кадре ничего не измеряется (иначе 47
  плиток заставили бы браузер пересчитывать раскладку по нескольку раз за
  кадр);
- строка `transform` считается **один раз на кадр** и раздаётся всем видимым
  карточкам: подъём у всех одинаковый;
- `will-change` ставится один раз на движение и снимается в покое;
- никакого React-состояния на кадр: карточка записывается в список
  (`src/motion/products-registry.ts`) и снимается при размонтировании.

Останавливается вместе с движком: шторка товара, корзина, спрятанная вкладка,
переход к категории — подъём снимается **мгновенно** (слой сам слушает паузы,
кадров-то больше не будет). «Уменьшить движение» и самый низкий уровень
качества — эффекта нет, тень и появление остаются.

## 23.09.2026 · Задача 15 — три правки по проверке на iPhone

Все три сделаны. Перед каждой сначала воспроизводил поломку, потом чинил —
ниже по каждой написано, что именно оказалось причиной и чем это доказано.

### 1. Качество линий фона

**Причина — не одна, а три.** Разобрал старую формулу
`line = 1 - smoothstep(0, uW * fwidth(v), g)` по частям и посчитал, что она
даёт на самом деле.

1. **Толщина зависела от направления линии.** `fwidth` — это не длина
   наклона поля, а сумма наклонов по горизонтали и по вертикали
   (|по x| + |по y|). У линии, идущей ровно вдоль оси, это одно число, у
   косой — в 1.41 раза больше. Из-за этого одна и та же линия на повороте
   становилась толще на 41% и обратно тоньше. Это и есть «толщина гуляет».
2. **Линия была тоньше одного пикселя, и без ровной середины.** Заливка была
   полной ровно в середине линии и сразу спадала к краям. Там, где середина
   линии проходила между центрами пикселей, экрану доставалась только бледная
   кромка. По моему замеру на экране iPhone **12.1% точек линии оказывались
   бледнее половины**, а самая бледная — 0.083 из 1. Это и есть «пунктир» и
   «разрывы».
3. **На телефоне линия была ещё и втрое тоньше, чем на компьютере.** Толщина
   считалась в пикселях холста, а не экрана. На компьютере холст был один к
   одному, на iPhone — полтора-три пикселя холста на один экранный, и линия
   во столько же раз худела.

Про «на пологих участках линия схлопывается в ничто» (версия из задания):
математически это не подтвердилось — множитель `fwidth` стоит и в пороге, и
в расстоянии, и сокращается. Схлопывалась линия не от пологости, а от трёх
причин выше. Деление на ноль на идеально ровном месте всё-таки возможно, и в
новой формуле от него стоит защита (`max(..., 1e-5)`), как и просили.

**Что сделано.** Толщина теперь считается честно — в пикселях экрана:

```
d    = g / max(length(vec2(dFdx(v), dFdy(v))), 1e-5)   расстояние до линии, px
line = 1 - smoothstep(uW - 0.6, uW + 0.6, d)           uW — полутолщина, px
```

Отличие от формулы в задании одно: вместо `fwidth(v)` стоит
`length(vec2(dFdx(v), dFdy(v)))` — настоящая длина наклона поля. Именно это
убирает причину №1: `fwidth` сама по себе гуляет на 41% по направлению, и с
ней «одинаковая толщина везде» недостижима. Смысл формулы тот же, что вы
описали словами: «расстояние до линии в пикселях экрана».

Мягкий край ±0.6 px — тоже из задания, и он же лечит причину №2: у линии
всегда есть не меньше 1.2 пикселя, на которых она видна, поэтому провалиться
между пикселями ей нечем.

**Перевод толщины.** `width` в `src/config/motion.json` теперь означает
полутолщину линии **в пикселях экрана** (было: безразмерный множитель).
Значение переведено с 0.6 на **0.38** — чтобы вид на компьютере не изменился.
Число не подобрано на глаз, а посчитано двумя способами, и оба дали одно:

- по формуле: старая толщина в среднем по всем направлениям равна
  0.6 × 1.273 = 0.764 пикселя, новая равна ровно 2 × uW, отсюда uW = 0.382;
- перебором: посчитал среднюю залитость всего экрана старой формулой и
  подобрал к ней новую — совпало на 0.380 (и на экране компьютера
  1440×900, и на экране iPhone; расхождение 0.4%).

Границы ползунка «Толщина» в панели стали 0.2…3 с шагом 0.02 (это пиксели), у
ползунка появилась подпись «полутолщина линии в пикселях экрана».

**Что это дало — числами.** Считал по той же математике, что в шейдере, на

### 2. Ошибка гидратации — закрыта

**Причина найдена и воспроизведена.** Сначала проверил напрашивающееся:
«сервер и клиент берут значение из разных мест». Это оказалось не так —
корневой layout считается только на сервере, клиент эти значения не
пересчитывает вовсе. Прогнал страницы в двух браузерах, включая WebKit
(движок Safari), с телефонным профилем — чисто. Проверил и версию «панель
переписала motion.json, а в браузере остался старый код»: записал новый цвет
через `/api/dev/motion` и перезагрузил страницу — тоже чисто.

Поломка нашлась с другой стороны. **Дело не в значениях, а в записи.** Все
переменные стояли одной строкой в атрибуте `style` у `<html>`. При гидрации
React сверяет этот атрибут с тем, что собрал сам, — **посимвольно**. Стоит
любому коду до гидрации тронуть `style` корневого элемента (а это делают:
блокировка прокрутки при открытии листа, панель `/dev/motion`, любое
расширение браузера), как браузер переписывает атрибут по-своему — с
пробелами после двоеточий. Значения те же, запись другая — и React считает,
что разметка не совпала.

Воспроизвёл ровно так: добавил в страницу скрипт, который до гидрации ставит
и убирает у `<html>` одно свойство. Ошибка появилась слово в слово, и в
списке расхождений первыми — те же самые `--color-cream: "#F7F2EA"`,
`--glass-bg`, `--glass-bg-fallback`, причём **слева и справа одно и то же
значение**. Это и есть подпись поломки: расходится не значение, а запись.
Так же ведут себя оба браузера — и Chromium, и WebKit.

**Что сделано.** У `<html>` больше **нет атрибута style вообще** — сверять
нечего, ошибка невозможна по устройству, а не по везению. Переменные приходят
обычным правилом `:root { ... }` в маленьком `<style>` в начале страницы
(новый файл `src/lib/root-css.ts`). Источник по-прежнему один: `motion.json`,
прочитанный на сервере. Клиент при гидрации ничего не пересчитывает.

Панель `/dev/motion` работает как раньше: она ставит переменные прямо на
`<html>` уже после монтирования, а такое значение сильнее правила `:root`.
Проверил живьём — цвет фона по кнопке в панели меняется.

Заодно убрал две функции, которые больше никем не вызывались и которыми эти
переменные можно было снова поставить в атрибут `style`

**Оба замка на месте.**

2. CSS: `touch-action: pan-x pan-y` у `html` и `body` — «можно только

**Тесты** (`e2e/viewport-lock.spec.ts`): мета-тег на пяти адресах, у `html` и

## Ложные заказы в Telegram: нашёл причину и закрыл её (24.09.2026)

### Что случилось на самом деле

Работал по правилам разбора: сначала факты из базы и от Telegram, только
потом выводы. Вот факты.

**В боевой базе сейчас всего два заказа, и оба настоящие:**

| № | Когда (Кишинёв) | Имя | Точка | Статус |
|---|---|---|---|---|
| 1679 | 22.09, 18:48 | Damian | Soroca Centru | не принят |
| 2109 | 23.09, 22:00 | MySushi | Soroca Centru | не принят |

Оба с вашего номера (+373 68 28 34 35), оба доставлены в Telegram
(у них записаны номера сообщений 44 и 46). Тестовых строк в базе не
осталось — 38 штук я удалил накануне.

**Напоминания из базы (pg_cron) не работают вообще.** В таблице `settings`
нет записи `telegram_reminders` — без неё функция `ping_reminders()` молча
выходит и сайт не зовёт. Подтверждение: у обоих заказов счётчики
напоминаний — нули, хотя они висят «не принят» больше суток.

**Боевого webhook у бота тоже нет.** `getWebhookInfo` отвечает пустым
адресом: бот сейчас живёт только через `npm run telegram:dev` на этом
компьютере.

**Номера заказов за сутки: 1679 → 2109.** За 22–23.09 израсходовано 430
номеров — это следы сотен заказов, созданных прогонами тестов и потом
удалённых.

**Главное место, где всё ломалось:** в `playwright.config.ts` стоит
`reuseExistingServer`. Если на порту 3000 уже висит обычный `npm run dev`,
Playwright не поднимает свой сервер, а берёт этот — а у него нет
переменной `APETIT_E2E=1`. Без неё подмены Telegram не существует, и
каждый заказ из теста уходил **настоящим сообщением в ваш чат**. А если
рядом был запущен `npm run telegram:dev`, он раз в минуту дёргал
напоминания по боевой базе — и лестница «⏰ заказ ждёт» (до 15 сообщений
точке и 3 владельцам на каждый непринятый заказ) шла по тестовым заказам.
Это и есть «всю ночь».

Так что гипотеза из задания верна наполовину: напоминания действительно
участвовали, но не из pg_cron (его нет), а с этого компьютера. А «одно-два
сообщения сегодня» — это карточка заказа, созданного тестом на сервере без
защиты. Косвенно сходится и по нумерации сообщений в чате: между 22.09
18:48 и 23.09 22:00 в чат ушло ровно одно сообщение.

### Как починено (не заглушкой)

Раньше защита была в переменной окружения сервера: «этот сервер тестовый,
он не шлёт в Telegram». Стоило прогону попасть на другой сервер — защиты
нет. Теперь **тестовость хранится в самом заказе**, и её видят все, кто
смотрит в базу.

1. **Миграция `supabase/migrations/0005_test_orders.sql`** — колонка
   `orders.is_test` (по умолчанию `false`) и более узкий индекс кандидатов
   на напоминание: тестовые строки в него не попадают вовсе.
   `place_order()` и выдача номеров не тронуты — пометка ставится
   отдельным UPDATE сразу после вставки.
2. **Пометить заказ тестовым может только сервер, поднятый тестами.** Три
   условия сразу (`src/server/orders/test-mode.ts`): сборка не боевая,
   `APETIT_E2E=1`, и заголовок `x-apetit-test` совпал с секретом
   `APETIT_TEST_SECRET`. Секрет придумывает сам Playwright при каждом
   прогоне и передаёт только своему серверу. В бою нет ни переменной, ни
   секрета — значит `is_test` там не может стать `true` никаким запросом
   снаружи.
3. **Telegram молчит по тестовым заказам** — проверка стоит у самой
   отправки (`notify.ts`), а не у вызывающего: обойти нельзя, откуда бы ни
   позвали.
4. **Напоминания их не видят** — выборка кандидатов фильтрует
   `is_test = false`.
5. **Уборка за тестами удаляет только помеченные строки**
   (`e2e/orders-db.ts`), да ещё и по своему имени и своим телефонам —
   настоящий заказ этой уборке не по зубам.
6. **Страховка, чтобы такое не повторилось.** Перед каждым прогоном
   (`e2e/global-setup.ts`) тесты спрашивают сервер: «ты подняли тесты?».
   Отвечает только маршрут `/api/dev/e2e`, и только при правильном
   секрете. Чужой сервер — прогон останавливается **до первого заказа** с
   понятным объяснением. Проверил руками: обычный `npm run dev` отвечает
   404 и с заголовком, и без.
7. **Вторая страховка, на уровне сети** (`e2e/telegram-guard.ts`): любой
   запрос к `api.telegram.org` из теста обрывается, и тест падает.
8. В боевой сборке маршрута `/api/dev/e2e` нет — это проверяет отдельный
   тест в `e2e-prod`.
