## Путь данных

1. Заказ: форма → Server Action → `submitOrder` → `place_order()` (advisory
   lock по телефону и IP, дубль, лимиты, INSERT) → ответ клиенту → `after()`
   → `notifyOrder`: чат точки из `telegram_chats`, HTML-текст, кнопка
   `accept:<uuid>`, 3 попытки, `telegram_message_id` / `telegram_error` в
   заказ; копии владельцам из `owner_chats`.
2. Событие Telegram → `/api/telegram/webhook`: заголовок
   `X-Telegram-Bot-Api-Secret-Token` = `TELEGRAM_WEBHOOK_SECRET` (сравнение за
   постоянное время, нет секрета → 401) → zod → `/start КОД` или callback.
3. Напоминания: pg_cron → `ping_reminders()` → pg_net POST на
   `/api/telegram/reminders` с `X-Reminders-Secret` → `claim_due_reminders()`
   (UPDATE … RETURNING поднимает счётчик атомарно) → sendMessage.

## Что проверено (OWASP Top 10:2025)

- **A01 доступ.** Оба маршрута закрыты секретом; чужой запрос → 401, тела не
  читаем. «Принят» проходит только из чата, привязанного к точке заказа
  (`wrong_chat` иначе). Новые таблицы — RLS без политик, права только
  `service_role`; функции — execute снят с `public/anon/authenticated`
  (anon-вызов `place_order` — 42501, проверено интеграцией).
- **A02 конфигурация.** Секреты только в `process.env`; `.env.example` без
  значений; токен — только в адресе запроса к Telegram, в ошибках и логах его
  нет (`TelegramError` хранит метод, статус и description). Подменённый
  отправитель для e2e включается только при `NODE_ENV !== production` и
  `APETIT_E2E=1`.
- **A03 цепочка поставок.** Новых npm-пакетов нет (Bot API — через `fetch`).
- **A04 данные.** `ip_hash` — HMAC-SHA256 с `ORDER_HASH_SECRET` (без секрета —
  SHA-256 и одно предупреждение в лог). Телефон и имя клиента уходят в
  Telegram по замыслу (SPEC §4.2) — только в привязанные чаты.
- **A05 инъекции.** HTML Telegram: имя, адрес, названия блюд и точки —
  `escapeHtml` (`& < >`); тест на `<b>`/`<script>` в имени и адресе; тест,
  что в готовых текстах бота нет `<`/`>` (живая проверка нашла это в
  подсказке «/start <cod>» — исправлено). SQL — только функции с параметрами;
  `lang` — zod enum.
- **A06 дизайн.** Лимиты атомарны (`pg_advisory_xact_lock`): интеграционный
  тест — 6 одновременных заказов с одного номера → ровно 3 приняты.
  Напоминания идемпотентны: два вызова подряд не дублируют. Код привязки —
  8 знаков из 31 (≈40 бит), неверные попытки логируются (без самого кода).
- **A09 логи.** «Кто принял» — id и имя пользователя Telegram, номер заказа,
  точка. Телефона и имени клиента в логах нет (тест).
- **A10 ошибки.** Telegram недоступен → заказ принят, ошибка в
  `telegram_error`; ошибка в webhook → 500, Telegram повторит; мусор → 400.

## Находки

1. **[HIGH → исправлено] Код точки как постоянный ключ.** Коды попадают в
   отчёт (и в git). Любой, кто знает код, мог отправить `/start КОД` и
   перепривязать чат точки на себя — с телефонами клиентов. Теперь код
   работает, пока точка не привязана; чужому чату — отказ
   («deja conectat»), тот же чат может повторить. Перепривязка — удалить
   строку в `telegram_chats` (потом — админка, SPEC §5.3).
2. **[MEDIUM, принято] Код владельца — многоразовый** (владельцев несколько,
   SPEC §4.4). Пока код действует, любой с кодом получает копии всех заказов.
   Рекомендация в отчёте: после подключения всех владельцев перевыпустить код
   одной строкой SQL (`update telegram_codes set code = random_link_code()
   where kind = 'owner'`).
3. **[LOW] Секрет напоминаний хранится в `settings` открытым текстом.**
   Таблица закрыта RLS и правами (только service_role/postgres); pg_net
   пишет ответы сайта в `net._http_response` — там только `{ok, due, sent}`.
   Альтернатива — Supabase Vault; не стал усложнять до публикации.
4. **[INFO] Telegram сам делает номер ссылкой** — отдельной кнопки «Позвонить»
   у ботов нет (SPEC §4.2).

Регрессий против прошлых ревью нет: цена только на сервере, ловушка/часы до
базы, номер при отказе не расходуется, `db_error` fail-closed.
