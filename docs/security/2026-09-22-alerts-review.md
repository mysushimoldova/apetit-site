## Что проверено (OWASP Top 10:2025)

- **A01 доступ.** Маршрут `/api/telegram/reminders` — прежняя проверка
  `X-Reminders-Secret` за постоянное время, нет секрета в env → 401.
  Новые поля — в уже закрытой таблице `orders` (RLS, права только
  service_role). Сообщения владельцам уходят только в чаты из `owner_chats`,
  которые заводятся кодом владельца.
- **A04 данные.** В тревогах и сообщении владельцам — только номер заказа,
  название точки, минуты и **телефон точки** (публичный, есть на сайте).
  Имени, телефона и адреса клиента там нет (по замыслу: эти сообщения могут
  прийти нескольким владельцам).
- **A05 инъекции.** Тексты собираются из чисел и названий точек из кода;
  подстановок от пользователя нет. Тест: в текстах бота нет `<` и `>`.
  Запросы — query builder с параметрами.
- **A06 дизайн (главное здесь).** Ступень «забирается» условным UPDATE
  (`claimStage`: `where status='new' and счётчик = expected`) — параллельные
  запуски cron не пришлют одно и то же дважды, а нажатие «Am preluat» между
  выборкой и отправкой отменяет ступень. Условие «прошло ≥ N и ступень не
  выполнена» — опоздавший cron ступень не теряет; за тик каждая дорожка
  двигается на один шаг, поэтому после долгого простоя не будет залпа.
  **Потолки — главная защита от «звонит всю ночь»**: `reminderMax` = 15
  напоминаний (30 минут) и `ownerMax` = 3 сообщения владельцам; когда обе
  дорожки пройдены, заказ выпадает из выборки самим запросом
  (`reminders_sent.lt.N,owner_alerts_sent.lt.M`), и забытый заказ замолкает
  навсегда без участия человека.
- **A09 логи.** `reminder/alarm/owner sent|failed` — номер, точка, ступень,
  число владельцев. Данных клиента нет.
- **A10 ошибки.** Ошибка на одном заказе не мешает другим (`Promise.all` с
  try/catch внутри); ступень при этом уже засчитана — сообщение не будет
  повторяться бесконечно, лестница идёт дальше. Ошибка целиком → 500,
  cron повторит через минуту.

## Находки

1. **[MEDIUM, принято] Ступень засчитывается до отправки.** Если Telegram
   ответил ошибкой, сообщение этой ступени потеряно (в логе `… failed`).
   Альтернатива — считать после отправки — даёт риск дублей при обрыве
   между отправкой и записью; для будильника дубли хуже, чем пропуск одной
   из шести ступеней (следующая придёт через минуту-две). Заказ при этом не
   теряется: он остаётся `new` и попадёт на следующие ступени.
2. **[LOW] Длительность запроса.** Пауз внутри больше нет (серии 🚨 убраны):
   за тик на заказ уходит максимум два сообщения точке и владельцам, всё
   параллельно — запрос заведомо короче лимита Cloudflare Workers (30 с).
3. **[LOW] `alerts.json` правится вручную.** Опечатка (ноль, отрицательное
   число, пропущенное поле) роняет сборку при загрузке конфига — тихой
   поломки напоминаний не будет.
4. **[MEDIUM → исправлено] Один чат в двух ролях.** Если чат записан и как
   точка, и как владелец (так вышло при живой проверке), он получал две
   одинаковые карточки заказа: с кнопкой и копию без кнопки — кассир видел
   внизу карточку без кнопки и не понимал, чем принимать. Теперь копия
   владельцам в чат самой точки не отправляется (`notify.ts`, тест).
5. **[INFO] Бот заблокирован пользователем.** Telegram отвечает
   `403 bot was blocked by the user`: заказ принимается и пишется в базу,
   причина — в `orders.telegram_error`, ступени идут дальше и упираются в
   потолки. Проверено вживую 21.09; увидеть такие заказы — запросом из
   отчёта в PROGRESS.md.

Регрессий против прошлых ревью нет: кнопка «Принят» по-прежнему принимается
только из чата своей точки; заказ, принятый кнопкой, немедленно выпадает из
всех ступеней (тест).
