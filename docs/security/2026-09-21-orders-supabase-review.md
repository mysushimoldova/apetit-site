## Путь данных

Как раньше до проверки позиций (zod strictObject → ловушка → точка → часы →
каталог точки). Дальше новое: `dedup_hash = sha256(телефон|точка#состав)`,
`ip_hash = sha256(IP)` → `findRecent` (дубль за 2 мин — вернуть записанный
заказ из базы) → `countByPhone` (≥3 за 10 мин — отказ) → `countByIp` (≥10) →
один `INSERT`, номер выдаёт sequence → снимок клиенту. Все запросы —
query builder supabase-js (фильтры PostgREST, параметризованы); в фильтры
попадают только нормализованный телефон и hex-хэши.

## Находки

1. **[MEDIUM, принято как ограничение] Лимиты не атомарны.** `count` и
   `insert` — два запроса: залп из N одновременных запросов с одного номера
   даст до N заказов вместо 3. Это защита от спама/опечаток, не от целевой
   атаки; по SPEC §9.4 при спаме включается Turnstile. Атомарно — только
   функцией в базе (insert + count в одной транзакции) — предложено
   архитектору.
2. **[LOW, вопрос архитектору] `ip_hash` без секрета.** SHA-256 адреса IPv4
   перебирается (4 млрд вариантов) — это псевдонимизация, не анонимизация.
   Лучше HMAC с секретом из env (новая переменная — сверх задачи).
3. **[LOW] Нагрузка на базу.** До отказа по лимиту — 2–3 запроса, принятый
   заказ — 4. Мусор, ловушка, «закрыто», чужая точка отсекаются до базы.
4. **[INFO] Тестовое время в базе.** В dev-сервере с `APETIT_E2E=1` заголовок
   `x-apetit-test-now` теперь задаёт и `created_at` строки. В production
   `testNow()` возвращает null до чтения заголовка — как было.

Регрессий против прошлого ревью нет: цена по-прежнему только на сервере,
ловушка/часы/пауза — до базы, номер не расходуется при отказе.
